<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Stripe webhook → payments table | Duplicate/replayed webhook events cross into the DB; idempotency must be enforced at the constraint level, not just the handler guard |
| Client refresh-token → refresh_tokens table | A leaked/replayed refresh token crosses into auth; rotation + replay-revoke-all must be anchored by the real token_hash UNIQUE |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01 | Spoofing/Elevation | refresh_tokens (RefreshTokenService) | mitigate | RefreshTokenRotationReplayTests asserts, against real Postgres, that replaying a rotated token revokes ALL the user's tokens — the in-memory provider cannot prove the token_hash UNIQUE that anchors detection (ASVS V2/V3) |
| T-07-02 | Tampering | payments.stripe_event_id (webhook idempotency) | mitigate | PaymentIdempotencyTests asserts the second insert of a duplicate stripe_event_id throws DbUpdateException(23505) against real Postgres — closes the in-memory false-confidence gap (RESEARCH Pitfall 7, ASVS V5) |
| T-07-03 | Tampering | receipt_files (user_id, content_hash) | mitigate | DuplicateDetectionTests asserts the composite UNIQUE rejects a duplicate upload at the DB level |
| T-07-04 | Information Disclosure | test connection strings / pepper in WAF settings | accept | Test-only placeholders (zero-byte pepper, sk_live placeholders) never reach production; container is ephemeral and disposed per RESEARCH Runtime State Inventory |
</threat_model>
