public class GetReceiptByIdHandler(IAppDbContext dbContext, ICurrentUser currentUser)
{
    public async Task<Result<ReceiptDto>> HandleAsync(
        GetReceiptByIdQuery query,
        CancellationToken cancellationToken = default)
    {
        var receipt = await dbContext.Receipts
            .Include(r => r.Items)
                .ThenInclude(i => i.Classifications)
            .Where(r => r.ReceiptFile.UserId == currentUser.UserId)
            .FirstOrDefaultAsync(r => r.Id == query.Id, cancellationToken);

        if (receipt is null)
            return Result<ReceiptDto>.Failure($"Receipt with id '{query.Id}' not found.");

        return Result<ReceiptDto>.Success(receipt.ToDto(includeRawText: true));
    }
}

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ClassifyBatchJob → Receipt.HasSumMismatch | Automated job sets flag; user dismisses via acknowledge-sum endpoint (Plan 04-03) |
| API → Frontend | hasSumMismatch is a read-only informational flag; no user can set it to true via API |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-04-01 | Tampering | HasSumMismatch flag manipulation | mitigate | HasSumMismatch can only be set by ClassifyBatchJob (automated) or cleared by AcknowledgeSumMismatchHandler (Plan 04-03) which checks ReceiptFile.UserId == currentUser.UserId. No user can set it to true via the API. |
| T-04-04-02 | Information Disclosure | HasSumMismatch in receipt DTO | accept | The flag only reveals that item totals don't match the receipt total — no PII exposure. Scoped to the authenticated user's own receipts via per-user data scoping on all receipt queries. |
| T-04-04-03 | Denial of Service | Items.Sum() on large receipts | accept | Receipts are bounded by parser output (typically < 100 items). LINQ Sum() on an in-memory ICollection is O(n) with negligible cost. |
</threat_model>
